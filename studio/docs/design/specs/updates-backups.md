# Updates, restore points and backups

Boards (canvas row *Updates, restore points, backups*): `LinkUpdate` with `LinkUpdateProgress`, `LinkUpdateDone`, `LinkUpdateRolledBack`; `LinkBackup`; `BrokerUpdate` with `BrokerUpdateRestart`, `BrokerUpdateDone`, `BrokerUpdateRolledBack`, `BrokerUpdateExternal`; `Backup` (clickable checkboxes) with `BackupProgress`, `BackupDone`, `BackupRestore`. Broker side: **ADR 0048** (proposed). The boards win for what is visible; this spec says where each screen sits, what it reads and calls, and its states.

**Order of work.** The broker parts come first. ADR 0048 §1 (package updates) and §3 (backups, link backup, broker restore, `send`) are built: §1, §2 and §4 below name the broker's values and actions as they are in the code (guides `docs/links.md` §5a and `docs/backups.md`). ADR 0048 §2 (broker self-update) is not built: §3 below is the plan, and its entry points stay hidden, never shown disabled with a promise.

## 1. Updating links (`LinkUpdate*`)

### Where
- Links page: a filter tab `Updates` with the count from the **attribute** `updates_available` of `sys/links` (in its `~meta`, beside `catalog`; it is not a child value: a child there would list as a link). Hidden at 0. It counts links, the rows of the tab. A row shows `from → to` in the version column (`to` in `emberSoft`); custom packages (the ones whose `latest` is empty) show `Update from file…` in the state column and are rows of the tab too; the count is of the links with an update. The board's line `The official repository was read … · Check now` is **not built**: no broker action reads the repository again and no value says when it was read (waiting for the broker).
- `Update all official…` in the page header: one review for every official package with an update, then the same progress per package, one after another.
- Link inspector, group *Version*: `Update to <v>` (ember) when its package has an update (`sys/packages/<name>/update_available`), `Update from file…` for a custom package, and `Versions and restore points`, which opens the same drawer on the result of the last update: restore points (`sys/links/<id>/restore_points`, rows `{at, version, size}`, newest first; a link replaced from a backup has one with an empty `version`) and `Roll back to <v>…` while the package has a `previous` (`{version, keep_until, changes_state}`). The broker has no download of a restore point: it is sealed for the broker and stays on it.

### Review (drawer 460 wide, board `LinkUpdate`)
- Title `Update <package> <from> → <to>`, pill `official` / `custom` (`official` = the repository index lists the package, `latest` is not empty; the index need not be the official one), sub-line: source, how many links run it, release date.
- `What is new in <to>`: the repository index carries no release notes yet, so the block shows the `title` and `summary` of the package's `catalog` row; `notes` lines and `Full changelog ›` appear when the index has them. Custom: the archive's `wyrm-link.json` `description` and version; no notes.
- `What changes for the broker`, one card each (dot: `warn` when it needs attention, `good` otherwise):
  - the links that restart (all links of the package, by id) and the expected pause; a WASM app with a hot start says `hot start, no restart`;
  - `Settings and nodes are kept` (Studio shows no counts: the board's `2 connections, 6 devices, 142 points` would need a read of every link's tree before the review);
  - new rights or network asked by the new version. The rows of `catalog` carry no `requester` or `net` and the broker has no dry run of an update, so the review cannot know them before the call: the first `update` goes **without `accept`**; when the new version asks for more than the links have, the broker installs nothing and its `message` lists them. Studio then shows that message in this card (warn) with the checkbox `Accept the new rights it asks for`, and the second call carries `accept: true`;
  - store format: `sys/packages/<name>/changes_state` (the update to `latest` changes it; ADR 0048 §1.7). A custom archive: its manifest's `reads_state` does not hold the installed `state`.
- `Before it starts` (checkboxes): `Save a restore point …` (on; locked on when the store format changes; no size estimate and no `keep_previous_days`: the broker shows neither, the result names `previous.keep_until`); `Roll back by itself if a link does not come back with all its nodes in 2 min` (on; `auto_rollback_s` 120 / 0); `Accept the new rights …` only after the broker's answer listed them (off; Update disabled until ticked).
- Footer: `Needs config on sys/links`, `Cancel`, `Update <n> links` → `sys/packages/<name>/~act/update {version, accept, restore_point, auto_rollback_s}`; custom → the primary is `Choose the archive…`, then `sys/links/~act/install_zip {name, zip, …}` with a link that runs the package and the same three arguments (a URL or a Git repository goes through Add a link ▸ a custom package). Both answer `{success, message}` at once; without `accept` and with new rights the message lists them and nothing is installed.

### Progress (`LinkUpdateProgress`)
The action answers once the links restarted; there is no progress stream. The steps before the answer (restore point saved, package fetched and checked, unpacked beside the old version, links restarted) show as one spinner (four rows: restore points, package, restart, health), then done once `last_update` is a new report with `result: checking`; the answer's `message` is shown under the steps. After it, Studio watches `sys/packages/<name>/last_update`: `result` is `checking` while the health check runs and `kept`, `new`, `gone` move (`n of m` nodes declared again, up to `auto_rollback_s`); it ends as `ok`, `rolled_back` or `failed`. While `checking`, another install of the package and its links' Start, Stop and Remove answer `busy`. Done = `good` ring, current = `ember` spinner, to do = `line3`. Footer: `You can leave this screen; it goes on.`, `Stop and roll back` (→ `sys/packages/<name>/~act/rollback`, which stops the check), primary disabled `Updating…`.

### Result (`LinkUpdateDone`, `LinkUpdateRolledBack`)
- Banner by `last_update.result`: `ok` → `Both links run 0.5.0` (good; warn with `reason` when `gone` > 0, which happens with `auto_rollback_s: 0`); `rolled_back` → `Rolled back to 0.4.2` (warn; the report of a rollback keeps the update's `from` and `to`, so the version the links run again is `from`) with `reason` (which link, how many nodes came back, or `rolled back by <who>`); `failed` → the new version stays, a link did not answer (warn, offer Roll back). `checking` is the progress screen, never a result.
- `Nodes before and after`: three tiles `kept`, `new`, `gone` and up to 10 of `new_keys` / `gone_keys` (`<link>/<path>`; `+` good, `!` warn), from `last_update`.
- `Restore points`: newest first; `Roll back to <v>…` (confirm dialog naming the links that restart, `last_update.links`) → `rollback {to, restore_data}`. Studio sends neither argument: the broker then restores the links' private data from the restore points of that update only when the update changed the store format, did not end `ok`, or lost nodes, and the links of an update that ended well keep the data they have (the confirm says so; `last_update.reason` says which was done). After a rollback `previous` is empty: no second rollback.
- Footer: audit names, `Close`, `Open <link>` or `Open the log of <v>` (System › Log, source the link, time of the update).

## 2. Backing up and restoring one link (`LinkBackup`)
- Link inspector ▸ `Back up…` → the backup dialog with link sections (`sections` names in brackets): `Settings` (`settings`, always), `Private data` (`data`: secrets and the private directory, the runtime edits of a driver among them), `Package` (`package`; **not offered for a link that runs a built-in driver**: the broker refuses it with `package: <id> runs the built-in driver …`), `History of its points` (`history`, range chips 7 / 30 / 90 / all → `history_days`). A link backup has no `estimate` action, so its rows show no sizes. Passphrase field: without one, `data` is sealed for this site and opens only on a broker with its keys (say so); with one (at least 12 characters, said under the field) it opens anywhere, and the field is disabled with the reason while `sys/backups` `export_secrets` is `false` and for a session that reaches the site through an upstream (`site.viewed != site.name`). Footer `config on sys/links`, `Back up <link>` → `sys/links/<id>/~act/backup {sections, history_days, passphrase}` → `{id}`: a job in `sys/backups` with `kind: link`; then the job's progress and download as §4.
- Restore: Links ▸ `Add a link` ▸ a third source `From backup` (beside official and custom, board `LinkInstall`): pick a `.wyrm-link`, Studio reads its `manifest.json` (the step *Check*: that it is a link backup, its link id, driver, mode and package, how it is sealed, its sections); the link's grants and net are in a sealed part, so they are **not** shown before the install: the first `install_backup` may go without `accept`, the broker's `message` then lists them and the wizard's *Change answers* comes back with `Accept requested rights`. Then: choose `id` (its own or a new one; an id that exists warns that the link is replaced in place after a restore point), the passphrase (kept in the wizard's own state, never in the store) → upload in parts (`sys/backups/~act/restore_begin {size}` → `{upload, part_size, max_part}`, `restore_part {upload, offset, data}`; Studio always uploads in parts and never sends `file`) then `sys/links/~act/install_backup {upload, id, accept, passphrase}` → `{success, message}`.

## 3. Updating the broker (`BrokerUpdate*`)

**Built behind one flag that is off** (`Features.brokerUpdate` in `business/lib/wyrm/features.dart`): the dialog, its state (`broker_update`) and the two actions exist and have goldens and tests fed by fixtures; the card `Broker version` is the one entry point and is not shown while the flag is off. Not built yet: the attention items, the entry from Sites, the offline banner's `Updating <site>`, and the dry run (`update?check`: the Dart client has no check call, so the review lists what the broker checks, without results). Assumed of the broker (ADR 0048 §2, to be fixed to the code when it exists): values `sys/latest`, `sys/update_state` (`none`, `staged`, `trial`, `confirmed`, `rolled_back`), `sys/update_last` (a map: `from`, `to`, `reason`, `down_s`, `links_back`, `links`, `back_s`, `rollback_until`), `sys/update_mode` (`self`, `external`), actions `sys/~act/update {version, confirm_site}` and `sys/~act/rollback_update`.

### Where
System › Maintenance: a card `Broker version` (first on the tab): `0.1.0 · 0.2.0 is available` (from `sys` `latest`, `update_available`) with `Update…`; when `update_state` is `trial` or a rollback is still possible, the card shows that state and `Roll back to <v>…` until `keep_days`. The System attention panel adds `Broker update available` (info) and `Update rolled back` (warn).

### Review (dialog 640, board `BrokerUpdate`)
- Title `Update <site> to wyrmd <v>`, pill `<from> → <to>`, sub-line: release date, channel, `the broker restarts once`.
- `Checked before anything changes` (from a dry run: `sys/~act/update?check` with ADR 0047): signature and SHA-256, the new binary's `check` of the configuration, room on disk, SCHEMA moves (warn: rollback restores the pre-update backup, later changes lost), links built for this broker (`wyrm_link`), standby (warn: update the standby first, with a link to it).
- `How it goes`: the five steps of ADR 0048 §2.4–2.6 in plain words.
- `Type <site> to confirm` (input; the primary stays disabled until it matches) → `sys/~act/update {version, confirm_site}`.
- Downstream sites: the same dialog from Sites › site ▸ `Update broker…` when the upstream has `allow_config` (else not shown).

### Restarting (`BrokerUpdateRestart`)
Studio loses the gateway on purpose. The dialog stays, with a spinner card `<site> is restarting on <v>` and a counter, and the steps as they are known (before the restart from the action; after, from `sys` `update_state` once the socket is back). `WyrmGateway.loginAny` logs in again by itself (ADR 0036 option 2); the shell's offline banner says `Updating <site>` instead of `Connection lost`. The text under the steps says what links and devices do meanwhile.

### Result (`BrokerUpdateDone`, `BrokerUpdateRolledBack`, `BrokerUpdateExternal`)
- Confirmed: banner (good), facts `Version`, `Without the broker`, `Links back`, `Roll back` (until), `Audit`; buttons `Close`, `Roll back to <from>…` (neutral; its own confirm with `Changes made after the update are lost`).
- Rolled back: banner (warn) with the reason from `update_last`, facts `Tried`, `Reason`, `Now`, `Log of <v>`, `Audit`; `Open the log of <v>`.
- External (`updates.mode: "external"`): no update button; the dialog says the image is changed where the container is defined, shows the two commands, and offers `Make the backup` (§4 with `control` + `keys`).

## 4. Backing up and restoring the broker (`Backup*`)

### Where
System › Maintenance: the card `Back up and restore` (today the copyable commands of `system.md`) becomes `Backups`: the kept backups (`sys/backups/<id>`: attributes `name`, `kind` (`full`, `link`, `pre-update`, `pre-restore`), `sections`, `sealed`, `link`, `by` (who made it); values `status`, `size`, `created`, `expires` (both **ISO 8601 texts**, UTC, not unix seconds), `sent_to`), newest first, each row with `Open`: the dialog of that backup with its download, its send and `Remove`; `Back up…` (primary) and `Restore…`. The card of the offline commands stays under it with the title `When the broker does not start` (a card, not a disclosure). A broker without `sys/backups` (a `wyrmd` before ADR 0048) shows the old card only.

### Back up (board `Backup`, clickable)
- Sections as checkboxes with their sizes (`sys/backups/~act/estimate {sections, links, history_days}` → `{sections: {name: bytes}, total}`); names from the attribute `sections` of `sys/backups`: `Control plane` (`control`, always, locked), `Keys and secrets` (`keys`, tag `passphrase`), `Dataflows` (`dataflows`), `Broker storage` (`storage`), `History` (`history`, range chips 7 / 30 / 90 / all → `history_days`; no custom range), `Links` (`links`, chips per link, all on → `links`; alarm records are the private data of the link `alarm`), `Installed packages` (`packages`), `wyrmd.json5 (read only)` (`config`: secrets masked, never restored). Unticked rows dim to 55 %.
- `Passphrase for the keys and secrets` (password field, at least 12 characters; without it `Keys and secrets` is unticked and disabled with the reason). The passphrase stays in the dialog's own widget state and goes to `create` as an action argument: it is in no Redux state, log or error text.
- `export_secrets` is an **attribute of `sys/backups`** (`backups.export_secrets` in `wyrmd.json5`, set on the host): while `false`, `Keys and secrets` and the passphrase field are disabled with that reason; link secrets are then sealed for the site and the file opens only on a broker with its keys. A session that reaches the site through an upstream (`site.viewed != site.name`) never gets `keys` or a passphrase, whatever the attribute says: Studio locks both with that reason before the call.
- `Where`: `This computer` (after the job is done, `Download…` asks for a folder and writes `<folder>/<name>` in parts: `download_part {offset, len}` from 0 until `eof`, 4 MiB each, one part in memory, a name that exists is never replaced; the SHA-256 of what arrived is compared with the backup's `sha256` and a difference is an error; `Cancel the download` removes the partial file), `File store link…` (only when the attribute `send_links` of `sys/backups` is not empty; its rows are `{link, folder}`: pick one of those links and one of its connections, show the folder the host named (read only), optionally a file name or sub-path below it; after the job is done → `sys/backups/<id>/~act/send {link, connection, path}`, then `send_status` `sending` / `done` / `failed` with `send_progress`, `send_error`; an existing name is refused, never replaced; not offered for a backup with `Keys and secrets`), `Keep on the broker` (kept `keep_days`, attribute of `sys/backups`).
- Footer: total size, `config on sys`, `Back up` → `sys/backups/~act/create {sections, links, history_days, passphrase}` → `{id}`.
- Progress (`BackupProgress`): a bar (`progress`), the current section (`step`), per-section rows when `step` names a section (done good, current ember, to do muted), the line about one consistent moment. The board's `day … of 30 · 196 MiB of 431 MiB · 1 min left` is not shown: the broker gives a percent and a step. Closing the dialog leaves the job running; the Backups card shows it.
- Done (`BackupDone`): file name, size, sections, SHA-256, how its secrets are sealed, who made it (`by`), the warning that the file and passphrase make an administrator (a backup with `keys`); the primary is `Download…`, `Send` or `Show in Backups` by the destination. Broker version and registry SCHEMA are in the file's manifest, not in `sys/backups/<id>`, so the dialog does not show them. A failed job shows the broker's `error` and `Remove`.

### Restore (board `BackupRestore`)
- `Restore…` ▸ pick a `.wyrm-backup` (upload in parts: `restore_begin {size}` → `{upload, part_size, max_part}`, `restore_part {upload, offset, data}` → `{received}`, parts of `part_size` and never above `max_part`, read from the file one at a time; `restore_abort {upload}` on cancel, on a failed part and when the dialog closes before the apply). `Check the file` then sends the passphrase the user typed (or none) → `restore_check {upload, passphrase}` → the checks, from its answer: `same_site`, `keys` (`none`, `same`, `differ`, `other`) with `keys_differ` (the key files that are not this broker's), `control_opens_here`, `schemas` (`backup` / `here`), `links` (`new` / `exists`), `problems` (each blocks `replace`), `notes`; and the file's `sections` as checkboxes (history off by default).
- `How`: `Replace what is ticked and restart the broker once (a backup of what it replaces is made first)` (`mode: replace`: `control`, `keys`, `dataflows`, `storage`, `history`, `links`, `packages`) or `Add only …; nothing replaced, no restart` (`mode: add`: `links`, `storage`).
- `Keys and secrets` in a restore is enabled only with `export_secrets`, a passphrase and a session on the site's own gateway. When `keys` is `differ` or `other`, a checkbox `Replace the site's keys` (`replace_keys`) names `keys_differ`; for `other` it warns that links, operators and peer brokers enrol again.
- `Accept the rights …` (`accept`) is a checkbox of the dialog from the start (the check does not say whether it is needed): without it a `restore_apply` whose links (`add`) or packages (`replace`) ask for rights is refused with the list.
- `mode: replace` is not offered to a session that reaches the site through an upstream (the broker refuses it), nor while the check lists `problems`; `add` is. A backup of another site name (`same_site: false`) cannot be applied at all.
- Footer: `Restore and restart` / `Add` → `restore_apply {upload, sections, mode, passphrase, accept, replace_keys}` → `add`: `{done, skipped, restart: false}`; `replace`: `{sections, restart: true}`, then the restart pattern of §3 (reconnect, then a result banner).

## 5. Data and calls (summary)
| Screen | Reads | Calls |
|---|---|---|
| Links › Updates | `sys/links` attributes `updates_available`, `catalog`; `sys/packages/<name>` values `version`, `latest`, `update_available`, `state`, `changes_state`, `previous`, `last_update` (`result`: `checking`, `ok`, `rolled_back`, `failed`) | `sys/packages/<name>` `update`, `rollback`; `sys/links` `install_zip`, `install_url`, `install_git` (custom) |
| Link inspector | `sys/links/<id>/restore_points` | `sys/links/<id>` `backup`; `sys/packages/<name>` `rollback` |
| Add a link ▸ From backup | the file's `manifest.json`, read by Studio | `sys/backups` `restore_begin`, `restore_part`, `restore_abort`; `sys/links` `install_backup` |
| System › Broker version | `sys` `version`, `latest`, `update_available`, `update_state`, `update_last` | `update` (`?check` first), `rollback_update` |
| System › Backups | `sys/backups` attributes `export_secrets`, `send_links`, `sections`, `keep_days`, `max_mb`; `sys/backups/<id>` attributes `kind`, `name`, `sections`, `sealed`, `link`, `by`, values `status`, `progress`, `step`, `size`, `sha256`, `created`, `expires`, `error`, `sent_to`, `send_status`, `send_progress`, `send_error` | `sys/backups` `estimate`, `create`, `restore_begin`, `restore_part`, `restore_abort`, `restore_check`, `restore_apply`; `sys/backups/<id>` `download_part`, `send`, `remove` |

All are config; the views check `site.needs('config', …)` and lock the buttons for others with the reason (Studio's rule).

**Transfers in parts** are one helper in `business` (`wyrm/transfer.dart`: `uploadParts`, `downloadParts`, `abortUpload`) on the broker's `restore_begin` / `restore_part` / `restore_abort` and `download_part` shapes, with progress and cancel. Arguments above the 64 KiB WebSocket frame go by the gateway's `POST /api/invoke` (the client does it by itself). Every long call shows its progress and survives closing the screen; errors follow `errors.md` (a timeout on `update` says the update may be running: Studio re-reads `update_state` before offering anything).
