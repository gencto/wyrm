# WYRM Studio

WYRM Studio is the app people use to set up and run a WYRM network: browse the tree, add links, let devices in, connect sites, edit flows, read history, manage access, and ask the assistant to do a change for them to approve. It lives in [`studio/`](../studio/). ADR 0037 records why it is built this way.

This document is the build plan. Each phase is one pull request. Every step says which `frx` command makes the artifact and what is written by hand.

**Which wins:** a board (its PNG, else its source) for anything visible, then the screen's spec in `studio/docs/design/specs/`, then this plan; where this plan disagrees with a board, the plan is wrong.

The reference for every screen is the **Studio design canvas** (Claude Design, owner's workspace); a snapshot of its boards is in [`studio/docs/design/`](../studio/docs/design/README.md). Boards are named in each section; a board with several states (a storyboard row) is one golden test per frame (§9). How to work on it, command by command: [`studio/docs/workflow.md`](../studio/docs/workflow.md).

## 1. Layout

```
studio/                 frx monorepo (Pub workspace), made by `frx create`
  app/                  entry, auto_route router, connectors (store → view model)
  ui/                   pages and widgets (data only), theme, icons
  business/             AsyncRedux: AppState, substates, actions, selectors, services
  models/               freezed models and enums (no dependencies)
  storage/              sembast key-value settings
  localization/         en, uk (intl_utils)
  docs/batches/         frx batch files of §4, applied in order
  docs/flows/           generated by `frx flow --md` (do not edit)
dart/wyrm_core          CBOR codec + fixtures (unchanged)
dart/wyrm_client        WyrmApi, WyrmGateway, ReconnectingClient (unchanged)
dart/wyrm_ffi           direct Zenoh access (unchanged, not used by Studio yet)
```

Dependencies point one way: `app → ui, business, localization`; `business → models, storage, wyrm_client`; `models` and `localization` depend on nothing. `wyrm_client` is a path dependency of `business` and not a workspace member (ADR 0037).

## 2. Rules

1. **`frx` makes every artifact and its wiring**: substate, field, selector, action, page, route, navigation hop, service, widget, connector, model, enum, theme extension. Writing one of these files by hand misses its wiring. Run `frx --help`; `frx new` asks for the arguments.
2. **By hand only inside bodies**: an action's `reduce()`, a service's `start()`, a widget's `build()`, a model's fields, a mapper.
3. **After every hand edit**: `frx doctor` (wiring, codegen, placement), then `dart analyze` in the package. Both clean before a commit.
4. **Codegen**: keep `frx watch` running (build_runner for the whole workspace, ~2 s per change). Localization is separate: `dart run intl_utils:generate` in `localization/`.
5. **Widgets get data, never state** (skill `data-driven-widgets`): `AppState → _Factory.fromStore() → _Vm → widget`. A widget never takes a `Store`, an `AppState`, a model from `models` or a `WyrmApi`. Text is formatted in the connector (`S.current…`).
6. **Pulled or pushed**: what the app asks for is an action (`deps.wyrm.invoke(…)`); what the broker pushes (values, list updates, connection, task progress) comes from a service and its dispatcher (§5).
7. **Errors**: an action that the broker refuses throws a `StudioException` (a `UserException`, `business/lib/wyrm/failures.dart`) carrying a `StudioError`: the broker's own message and its `status` as a `StatusCode` (`{success, message}` → kind `broker`), never flattened into text. Calls go through `call` / `listOf` / `metaOf` / `invokeAll` (a write) / `askAll` (a read) of `business/lib/wyrm/calls.dart`, which name the key and the call; `Action.wrapError` gives every failure its id, time, site, words (`ErrorWording`, the app's `wordError`) and what *Try again* / *Refresh* dispatch (`Action.again()` / `reload()`), and `Action.after` adds it to `problems`. Never swallow a refusal: a quiet one goes to Problems. Which surface shows it (inline, dialog, toast + Problems, panel card, start screen), the kinds and the words: `studio/docs/design/specs/errors.md`.
8. **Rights decide**: Studio never hides a broker rule. A control the user's role cannot use is shown disabled with the reason (`needs config on sys`), not removed.
9. **Agents**: open Claude Code in `studio/`; its `CLAUDE.md`, 30 skills and the `guard-wired-files` hook load there. The repository's own skills (`wyrm-agent`, `wyrm-flow`, `wyrm-link`) are for the broker side.

## 5. Connection layer

### 5.1 Login and session
`LogInAction` (waiting; not blocking since the log-in page shows its own progress, `studio/docs/design/specs/login.md` §3.6–3.7):
0. A timed `GET /api/me` of each gateway until one answers (`WyrmLogin.probe`); none answers → `login.failure` = `unreachable` with the reason. `login.step` follows the page's three steps (0 reaching, 1 checking, 2 reading); a refused password → `login.failure` = `wrong`. Both are thrown as `StudioException`s without a dialog (`withDialog(false)`: a line in Problems, no toast): the page shows them inline. An empty or malformed field is the form's to say under the field; `LogInAction` dispatched without that changes nothing.
1. `WyrmGateway.login(Uri.parse(gateway), user: user, password: password)`; for several gateways (standby, ADR 0036) `WyrmGateway.loginAny([...])`.
2. `gw.me()` → `site`, `role` into `SiteState` (`SetGatewayAction` and the fields of phase 2).
3. `gw.client()` → a `ReconnectingClient`; hand it to `WyrmConnectionService.attach(client)` (§5.2).
4. `session.token` = the gateway session (the auth guard reacts to it). The password is never stored; the gateway URL and user are (`storage`, settings), and the last five gateways that logged in (`login.recent`) — all three only while `login.remember` is on.

After it the page shows the welcome and dispatches `OpenTreeAction`, then goes to the Studio shell. `OpenTreeAction` preloads, in this order, what the first screens need (`studio/docs/design/specs/login.md` §5.1): the tree root (live lists of `downstream`, `dataflows`, `storage`; only `downstream` opens in the tree), the flows, the flow block catalogue (`flows.blockTypes`, kept for the session and the site; `LoadFlowAction` reads it first, `ViewSiteAction` clears it), the links and the site choices. Each step waits at most 2 s, the whole welcome at least 600 ms and at most 5 s; what is not ready goes on in the background. The preload dispatches its reads with `quiet = true` (`Action.quiet`, set per dispatch): a failure is logged and fails the dispatch, but opens no dialog: it is a toast and a line in Problems (`studio/docs/design/specs/errors.md` §4). `ProbeGatewayAction` probes the gateway field on open, on a recent chip and on leaving the field (`login.probes`: ms, -1 no answer).

`LogOutAction`: close the client, clear `session`, `site`, every table (`*.table` back to empty), stop the services' subscriptions.

### 5.2 Services
Each service is two halves (template rule): `<Name>Service` talks to `WyrmApi` and knows nothing of Redux; `<Name>Dispatcher` holds the store.

| Service | Opens | Dispatches |
|---|---|---|
| `WyrmConnectionService` | `ReconnectingClient.connection` (`Stream<bool>`) | `SetConnectedAction(value)`; on `false` the shell shows the offline banner; on `true` again every screen's Retrieve action reruns |
| `TreeWatchService` | `list(key)` for each expanded node (`nodes.expanded`), closed when collapsed; also `dataflows` and `storage` from the log-in preload (§5.1), listed without being expanded. A list that answered once is in `nodes.listed` | `ListUpdate` → `AddNodesAction` (Refreshed/Added/Changed) and a remove; `Disconnected` → mark the branch stale |
| `LiveValuesService` | one `subscribe(key)` per key in `live.watched` (opened and closed as the set changes) | buffers `ValEvent`s; at most every 200 ms one `SetLiveValuesAction(IMap<String, LiveValue>)` with the changed keys only, then the same batch to `AppendSamplesAction` (History's trend) and `ApplyFlowValuesAction` (Flows' definitions), each a no-op while its tab is hidden |
| `LiveListsService` | `list(key)` for each key in `live.lists` (reader counts, like `live.watched`): the lists a shown screen follows, apart from the Explorer's `TreeWatchService` so neither closes the other's; a list that lost its broker or ended is opened again after 5 s | `ListUpdate` → `ApplyHistoryListAction` (`sys/history`, `sys/history/<group>`) or `ApplyFlowsListAction` (`dataflows`), by key; an update of a site no longer on screen is dropped; a failure is as in the tree (`permission_denied` = an empty list, another refusal empties it and is a quiet problem, a lost broker keeps what is shown) |
| `AgentTasksService` | `subscribe('wy/<site>/downstream/<agent>/tasks/*/~val')` (public: `{state}` only), then `get` of `tasks/<id>` `~state` for the ones in view | `AddTasksAction` with the full record when the state changes |

`WatchKeysAction`/`UnwatchKeysAction` are dispatched when a screen's tab is shown and hidden (`TabVisibility`, §5.3 item 4; the keys the screen shows), so only visible points are subscribed. A screen that follows more than one fixed set keeps what it follows in its slice as a `LiveSet {values, lists}` (`historian.follow`, `flows.follow`; null while hidden) and moves between sets with `FollowAction(from, to)`, which watches and unwatches only the difference; so a hide, another group, other points or a site switch close exactly what the screen opened, whatever `site.root` reads by then. A connector that shows values selects `live.values` filtered to its own keys, so a value elsewhere does not rebuild it.

### 5.3 Decisions of phase 5 (2026-11-08)
These hold for every screen; each was decided under ADR 0029 (decide, record, do not ask).

1. **The site on screen is not the site logged into.** `site.name` is the gateway's site (`/api/me`); `site.current` is the one picked in the top-bar switcher (null = the same). Every screen reads its keys from `site.root` = `wy/<current ?? name>`; `site.home` stays the gateway's. The switcher's list (`site.choices`, `RetrieveSitesAction`) is the site itself, every broker below it (`downstream/<d>` of profile `wy:broker`, `attr.site`, up to 4 hops, with the site it is relayed through) and the brokers above it (`sys/upstream/*`). `ViewSiteAction` empties the per-site tables and reads them again.
2. **The user's rights are kept.** `/api/me` `grants: [{k, p}]` go to `site.grants`; `site.levelOn(key)` is the highest level whose pattern matches (`*`, `**`, `wyrm/keys.dart`), `site.needs(level, key)` the reason shown on a disabled control (rule 8). The gateway rewrites grants for a downstream site, so the patterns are full keys.
3. **Stage, then apply once** (canvas *Design system* §01, §06). Edits of values and parameters become `StagedChange`s in the `changes` slice (op, key, field, from, to, level, and the `set` value or the `invoke` action and args); a second edit of the same key and field replaces the first and keeps its `from`. The top bar's *Review and apply* shows the count (disabled at 0); the review panel lists the change cards with the level each needs against the user's grants. `ApplyChangesAction` runs them in order with the user's own rights and stops at the first refusal: applied ones leave the list, the refused one and the rest stay, the broker's message is shown. Actions that do something now (Start, Remove, Install, Approve) are not staged.
4. **Live values follow the visible tab.** The tabs shell keeps visited tabs mounted, so a screen watches its keys through `TabVisibility` (watch when its tab becomes active, unwatch when it stops), not through `onInit`/`onDispose`. `live.watched` counts readers per key or pattern (`IMap<String, int>`), so two parts of a screen on the same key do not close each other's subscription.
5. **Navigation after log in and log out is explicit** (`GoAction.replace`): auto_route 11 re-runs the auth guard on the token's listenable but does not redirect away from an already resolved route. The guard still keeps a logged-out user out of the shell.

### 5.4 Calls
All calls go through `deps.wyrm` (the `WyrmApi` of the session): `invoke(key, action, args)` is a stream (an action may answer several rows); `set(key, value)`; `meta(key)`; `children(key)`; `history(key, …)`. A large argument (a package zip, a file) goes over `POST /api/invoke` by itself (`FrameClient`, 64 MiB). An action wraps them in `call(name, key, …)` or one of its helpers (rule 7), so a refusal keeps its key, call and status; a stream that fails (`LiveValuesService`, `TreeWatchService`) reports to its dispatcher, which marks the row (`live.failed`) and adds a quiet problem, and a subscription that lost its broker is opened again every 5 s.

### 6.7 States: first load and refresh (stale while revalidate)
One rule for every workspace (decided 2026-11-08):

1. **First load** — a read is in flight and the workspace holds nothing yet: the workspace shows its own empty or loading state (`Loading…` in the table, an empty log, a skeleton).
2. **Refresh** — a read is in flight and the workspace already holds data (a tab shown again, a site reconnected, a list read again): the content **stays on screen and stays usable**. A thin indeterminate strip (`RefreshFrame`, 2 px, ember, the log-in bar's sweep, 1.4 s) lies over the top edge of the workspace content, so nothing moves, and where the workspace has a status line — the line under a `PageHeader` title — it ends in `· Updating…` (12, `text4`). Under reduced motion the strip stands still at 60 %. Assistive technology reads `Updating…`.
3. **At rest** — no strip, no label.

Where it is built: `refreshing(Workspace)` in `SelectComposites` (`business/lib/redux/selectors.dart`) is true when one of the workspace's `Retrieve…` actions is in `Wait` **and** its slice holds data; commands in flight (Start, Deploy, Install, Apply) do not count. `StudioPageConnector` puts the set of refreshing workspaces in its view-model and wraps the active tab in `RefreshFrame`; `PageHeader` reads the label from the frame (`RefreshScope`). A `Retrieve…` action never empties its table before its answer arrives; a connector never shows `Loading…` while it holds data.

| Workspace | Reads that count | Holds data when | `Updating…` shown |
|---|---|---|---|
| Explorer | node detail, node history, links | `nodes.table` | no status line: strip only |
| Links | links, quarantine, packages | links or quarantine | header line |
| Flows | flows | `flows.table` | header line |
| History | historian, series | watch groups | no status line: strip only |
| Access | users and grants | users or grants | header line |
| Sites | peers, sites, quarantine, links | peers or site choices | header line |
| Assistant | agent, tasks | tasks or the agent | no status line: strip only |
| System | log (`Get log`, a toolbar change; not the 5 s poll), profiles | log lines or profiles | no status line: strip only |

Golden: `ui/test/goldens/links_refreshing.png` (the Links board, refreshing, the strip half way).

- **Binding is drag and drop along a wire**: the canvas reads the pointer itself (`FlowCanvas`, one `Listener` around the `InteractiveViewer`, pointers mapped through its transform, geometry from `FlowBlockVm`), so a dragged block or wire stays under the pointer at any zoom and scroll. Press a field (its right port or anywhere on its row) and move 3 px: an S-curve follows the pointer from the field's right port; a row that takes it lights teal and the wire snaps to its left port; a row that refuses lights red and a chip by the pointer says why (`Outputs cannot be bound`, `Factor takes no input: type its value`, `A block cannot feed itself`, `number does not fit bool`, `This closes a loop (only a delay may)`; `bindRefusal` in `flow_fields.dart`, the engine's port types and validation step 5); let go on it, it binds (`ConnectPortsAction`, one wire per input); on the empty canvas, nothing. On a bound input the left port (or the whole row of a field without an output) picks its wire up: let go on another input, it moves there (`RebindEdgeAction`); on the empty canvas, it unbinds (the parameter keeps its last value). A double click or an Alt-click on a bound input unbinds; so does the inspector's link icon. A wire let go on a row of the inspector binds that field (`FieldDropZone`, found by a hit test; a new wire only: a picked-up wire moves between canvas inputs, and the inspector does not check the refusals, validation does). Wires are drawn behind the blocks, the selected block's on top. The header moves a block, snapped to the 20 px grid when let go; a palette entry lands with the pointer on its header; the empty canvas pans, and so do two fingers on a trackpad (pinch and the wheel zoom).
- **Forms:** a type that does one of two things shows the form in use (`BlockForm`, `formsOf`): `scale` is `k × in + b` (Factor, Offset) or `Range` (Input min … Output max, `Input out of range`); the inspector's `Form` row picks it (`SetBlockFormAction`): the other form's parameters and the wires into and out of its fields leave the definition, and the range form writes its four parameters (the definition then says the form). A loaded definition with both forms shows both.
- **Live values the watch has not seen:** the engine records a port from its first sample after the watch opened, so a slow point or a value sent once at start is absent there. The editor still shows what is known, for the deployed version only: an input fed by a deployed wire shows its source's value, a variable (`number`, `string`, `bool`, `const`) its `value`, an echo its parameter, a `publish` input and the output wired straight into it what the block last published (`dataflows/<id>/nodes/<node>`).
- A wire from a parameter's echo into `set`/`invoke` carries a `fires at deploy` chip (a parameter's echo sends at start, ADR 0038 §6).
- Top bar: `Draft saved` (teal dot) while the draft differs from the deployed version (compared as definitions), else `Version <n> · deployed` and Deploy outlined and off (`Nothing to deploy`). The draft lives in the store: closing and reopening the same flow keeps it while the broker has no newer version; it is not written to disk.
- **Tree tab (owner requirement 2026-11-09; `flow-editor.md` §18):** the site's real tree, drawn with the Explorer's own rows (`ui/lib/trees/tree_row.dart`, 32 high) from the same live lists (`nodes.table`, `nodes.expanded`, `TreeWatchService`): `downstream`, `dataflows`, `storage`. Extended for the editor: a value node IS a row (type tag, mono name, live value), and an open node lists its actions first (ember `ACT`, name, `<n> in`; from the node's `~meta`, read once when the node is first opened here, `RetrieveDetailsAction`, never an action of level config). The search field filters the rows where they are made (`flowEditor.treeQuery`). A value dragged onto the canvas → `subscribe` (a writable one asks `Read` or `Write` where it lands; Alt writes at once → `set`); onto a field → a `subscribe` wired into it; an action → the action block. The mapping is `blockOfEntry` (`business/lib/wyrm/mappers/flow_blocks.dart`).
- Validate as you edit: `invoke('dataflows', 'validate', {def})` (debounced, `ValidateFlowAction` with `debounce`); Deploy: `invoke('dataflows', 'deploy', {def})` with `version` + 1 and `layout`; the gateway adds the proofs (ADR 0008, 0033).
- **Canvas tools (owner decisions 2026-11-09;** rules and tables in `studio/docs/design/specs/flow-editor.md` §12–§15**):**
  - **Pins.** A block draws its pinned fields; the inspector lists every field with a pin before its label. Defaults per type (`FlowField.onBlock`); a bound field is always a row and is pinned for good when it gets its wire; `Unpin from block` on a row's menu, `Fields ▸` on a block's. Kept in the definition's `layout` as `"<node>~pin~<field id>": [1 | 0, 0]` beside the positions (`pinKey`), so it deploys on today's engine, which reads `layout` as pairs of numbers and ignores the keys; spec 06 names the key a node id, so this shape is the owner's to confirm or to replace by a spec change. `SetFieldPinAction`.
  - **Selection.** `flowEditor.selection`; a marquee on the empty canvas, Shift- or ⌘/Ctrl-click, ⌘/Ctrl+A; a header moves the whole selection (`MoveBlocksAction`, one undo step). Panning is Space + drag, the middle button, the wheel and two fingers; zoom is ⌘/Ctrl + wheel, a pinch and the keys, 25 % … 200 %. The canvas pans and zooms its own transform (the `InteractiveViewer` only holds it) and reads every pointer through it.
  - **Context menu** (`FlowMenu`) of a block, the selection or the canvas: Cut, Copy, Paste (at the pointer), Duplicate, Delete, Select all, Undo, Redo, `Fields ▸`, `Unpin from block`, `Create custom block…` (a selection) and `Edit custom block` (an instance); the last two are off with the reason on a broker without custom blocks.
  - **Clipboard.** The editor's own (`flowEditor.clipboard`, kept from one flow to the next) and the system's, as JSON `{"format": "wyrm-flow-blocks/1", nodes, edges, layout, blocks?}` (a part of a definition; only edges among the copied blocks; `blocks` holds the definitions of the copied instances' custom blocks and all they use, so an instance pastes into another flow with its definition). Paste makes ids unique (`scale1` → `scale2`) and selects what it pasted; a text of another kind pastes nothing. `PasteBlocksAction`, `RemoveBlocksAction`, `SetClipboardAction`.
  - **Undo and redo.** 100 steps of the draft (`undo`, `redo`; `UndoFlowAction`, `RedoFlowAction`); every canvas edit is a step, typing in one field and a run of arrow keys are one step each; the id and the version are not undone.
  - **Shortcuts.** One table (`flowShortcuts`, `ui/lib/flows/shortcut_card.dart`) read by the key handler, the pointer gestures, the menu's hints and the card (`?` button beside the legend, `?` key). Keys are off while a text field or the value viewer has the focus and while a dialog is open. ⌘/Ctrl+Enter deploys after a confirmation; `/` and ⌘/Ctrl+K put the cursor in the palette's search.
- **The second wave (owner requirements 2026-11-09, ADR 0040;** rules in `flow-editor.md` §17–§20, the per-type table in `docs/flow-blocks.md`**):**
  - **What the broker can do** is read, never assumed (`FlowCaps`, `flowCapsOf`): a parameter with `scope` in the catalog (a key from a port), a type with `trigger: true` (Run), `dyn_inputs.keys` (argument ports), and `list_blocks` answering (`flowEditor.libraryOff` is null). On a broker without one of them the feature is shown off with the reason and the editor draws the older shape; nothing is hidden and nothing breaks.
  - **Keys from a binding.** `Point` of `subscribe`, `liveliness`, `load_value` and `Node` of `list_children` are fields with a left port. A wire into one opens the scope's prompt on the field (`ScopePrompt`, `flowEditor.scopePrompt`): the key's parent and all below it proposed, the site's sections as chips, the engine's rule checked as typed (`scopeProblem`); Save writes `key_scope` / `path_scope`, Cancel takes the wire away. The scope is then a row `Scope` with a pencil; `Error` is a row while the key is bound; unbinding keeps the scope and the last key.
  - **The action block.** One block (`invoke`; the same groups for `set`, `load_value`, `list_children`). Its header reads `<node> · <action>`; its rows by default: the required arguments, `Trigger`, `Ok`, `Error`. The inspector groups its fields: Target · Arguments (each typed as the action's `~meta` says, or bound through `arg.<name>`) · Behaviour (`Trigger`: bound, or a `Run` button; `Auto run`; `Every` with its unit; `Enabled`; `Run on start` behind a confirmation with the catalog's `WARNING:` text) · Events (`Sent`, `Ok`, `Error`: when each last fired, an error's code and message) · State (`Running`, `Last run`, `Result`). `Run` calls `dataflows/<id>` ▸ `trigger {node}` on the DEPLOYED flow (`TriggerBlockAction`): off with the reason while the draft differs from it, the flow is not deployed, or the user lacks write; a refusal is said in words (`permission_denied` has no text).
  - **Custom blocks.** `Create custom block…` asks a name, a description and a name per port (an input may get a default) and replaces the selection by one instance (`createCustomBlock`, on top of `extractSubflow`; the definition goes into the flow's `blocks`). An instance draws with the `MY` chip, its declared inputs and outputs as fields and `Open inside`. `Edit custom block` / `Open inside` show the block's inside on the same canvas (`flowEditor.frames`, `EnterBlockAction`, `LeaveBlockAction`): the path reads `Flows › <flow> › <block>`, `Back` returns, an `Inputs` block and an `Outputs` block stand for the boundary (a wire from `Inputs.<a>` is the input's `to`, a wire into `Outputs.<x>` the output's `from`; − / + take or add a port), and the bar says how many instances the change reaches. Validate and the preview always read the whole flow (`flowEditor.root`); Deploy waits for `Back`. Live values inside come from the rows `<instance>/<inner>`. The My blocks tab lists the flow's blocks and the site's library (`list_blocks`); a library block placed is COPIED with the blocks it uses (`get_block`, `PlaceLibraryBlockAction`); the menu of an entry: `Edit custom block`, `Save to library` (`put_block`, level config, the blocks it uses first), `Rename`, `Update from library` (when the library's version is not the copied one, kept as an editor key of the block's `layout`), `Delete` (only unused).
  - **New blocks** of ADR 0040 §4 are in the palette under the catalog's categories, each type in words (`rising_edge` → `Rising edge`, `blockLabel`; the engine's name is searched too).
- Repeat needs engine support (§10 item 9); until then it stays design-only and is not in the palette.

### 7.7 History, Access, System
- **History** (board *History · watch groups and trends*): while the tab is shown (`FollowHistoryAction`, owner report 2026-11-12) the groups come from the live list of `sys/history` and the selected group's watches from its live list; a group added elsewhere is read once for its watches (`RetrieveGroupWatchesAction`; the other groups are not listed live), one removed leaves the sidebar, and the selected one removed selects the first left. The historian's values (`sys/history/*`: rows written, size, oldest day, retention) and every group's settings (`sys/history/*/*`) are live values (`SelectHistorian.shownStats`, `shownGroups`). Each picked point's `~val` is subscribed: a sample newer than the series' last point extends its trend (`AppendSamplesAction`): in the bucket of the last point (range / 300) it takes its place, else it is a new point; points older than the range drop off, so a trend stays about 300 points however long it is open. Hide, another group, an unpick and a site switch close what they no longer need. Recorded values (`history(key, …)`, about 300 buckets per range) are read only for the points the user picks (owner 2026-11-11): a click on a point row shows it alone, ⌘/Ctrl-click adds or takes off one, at most three on one trend; with none picked the trend says *Pick a point to see its trend*. A range change and a refresh read the picked points again; another group starts with none. A row click runs no action: Stop recording (`unsubscribe`) is in the inspector while one point is picked. The trend is a custom painter (rows ≤ 5000 per answer).
- **Access** (board *Studio · Access*): gateway users (`/api/users`), roles, `sys` ▸ `get_permissions`, `update_permissions {role, path, level}`, audit tail `sys/audit` ▸ `tail {n}`. `/api/users` has no stream, so while the tab is shown (`access.shown`) `PollAccessAction` reads all three again every 10 s (`Every` in the connector), and `RetrieveAccessAction` once when it is shown. The poll is not in `Wait` (no sweep bar), runs one at a time and is silent: a failed poll keeps what is shown and the next one tries again. The selection, the tab and the open inspector stay across polls.
- **System** (boards `System`, `SystemAvail*`, `SystemLog`, `SystemMaint`; spec `studio/docs/design/specs/system.md`): four tabs and an attention panel beside each (under the main column below 1100 px).
  - **Overview**: every `sys` value as a tile (`SysTile`: label, key, value, unit, one line; the node's `description` as tooltip, read once per site by `RetrieveSysAboutAction`); a tile with a destination is a link (Links, Links › Quarantine, Sites, History, Access › Audit). Router traffic: `TrafficService` ticks every 2 s while Studio runs, `SampleTrafficAction` keeps the six rate keys of the site on screen watched and adds a sample per value the broker publishes (`system.samples`, one hour); the switch Messages / Frames / Bytes is `system.measure`.
  - **Availability**: read only. `standby` in `SelectBrokerHealth` (unknown / none / following / behind) from `standby_connected`, `standby_lag`, `standby_forks`; `arbiter_lease_s` = 0 shows `—`, at or below 3 s "renewing late" (proposed).
  - **Log**: `RetrieveSystemLogAction` = `sys/~act/get_log {lines, level, filter, link}` from the toolbar (`system.lines` 200, `logLevel`, `filter`, `source`); a refusal goes to `system.logError` and the log box, not a dialog; `PollSystemLogAction` repeats it every 5 s while the tab is shown (not in `Wait`, so no sweep bar); Copy and Save as .log write `<time> <LEVEL> <target> <message>` lines (`wyrm-<site>-<yyyymmdd-hhmm>.log`; macOS entitlement `files.user-selected.read-write`). Picking a broker log level stages `sys/log_level` (the enum index, level `config`) in Review and apply.
  - **Maintenance**: `clearableLinks` is the broker's own `clear_conns` rule (external, `attr.origin` runtime, not connected); `ClearConnsAction` after a confirm that repeats the ids, its answer as a toast. Profiles: `RetrieveProfilesAction` (`children(pub)`, each `pub/<name>` meta), `PutProfileAction` (`.cbor` as it is, JSON encoded by `profile_mapper.dart`), `RemoveProfileAction`. Backup commands are text to copy.
  - **Attention panel**: `attention` in `SelectBrokerHealth`, in the spec's order; `system.aclSeen` is the ACL counter when the screen was last left.
  - `sys/allow_all_links` and `sys/enable_quarantine` are not here: their switches are in Links › Quarantine.

### 7.8 Assistant
Boards: row *Assistant* (Ask, Plan, Running, Done, Stopped, What it may do, In Explorer). Tab: assistant; a drawer in Explorer (⌘J). State: `tasks`, `assistant`.

## 9. Tests and CI
- `business`: action tests with a fake `WyrmApi` (records calls, replies from fixtures), selector tests, mapper tests.
- `ui`: golden tests per canvas frame; the Vm of each frame lives in `ui/test/frames/<board>.dart` so a frame is data.
- `app`: connector tests (`fromStore` → Vm).
- CI job `studio` in `.github/workflows/ci.yml` (a gate since its first green run, PR #10; the frx installer is pinned to the commit of tag v0.3.7):

```yaml
  studio:
    runs-on: ubuntu-latest
    timeout-minutes: 25
    permissions:
      contents: read
    defaults:
      run:
        working-directory: studio
    steps:
      - uses: actions/checkout@v4
        with:
          persist-credentials: false
      - uses: subosito/flutter-action@v2
        with:
          channel: stable
          cache: true
      - name: Install frx
        run: |
          curl -fsSL https://raw.githubusercontent.com/pro100andrey/flutter_redux_templates/d2bbfaedc6c9710468e8215a063f1430d16ba73a/tools/scripts/install.sh | sh -s -- --version 0.3.7 --no-modify-path
          echo "$HOME/.frx/bin" >> "$GITHUB_PATH"
      - run: flutter pub get
      - run: dart run build_runner build --workspace
      - run: frx doctor
      - run: flutter analyze
      - name: Tests
        run: |
          for p in app ui business models storage localization; do
            if [ -d "$p/test" ]; then (cd "$p" && flutter test); fi
          done
```
- Before a PR: `frx doctor`, `frx flow --md` (the flow docs are checked by doctor), `frx graph --fail-on-orphans`.
- The job takes the newest stable Flutter (`channel: stable`, no version): its analyzer can be stricter than a local SDK (2026-11-09: Flutter 3.47.9 in CI, 3.44.4 locally; 3.47's linter flags a conditional expression inside a `for`/`if` collection element (`prefer_if_elements_to_conditional_expressions`) and `unawaited(...)` around a call annotated `@awaitNotRequired` (`unnecessary_unawaited`), which 3.44's `discarded_futures` still asks for). Before a PR, run `flutter analyze` from `studio/` with the current stable too (`puro`/`fvm`), then restore `pubspec.lock` and `flutter pub get` with the local SDK. Code clean on both: an `if`/`else` element instead of `?:` in a collection, `controller.forward().ignore()` for a ticker started from a sync method.

## 10. What the broker side still needs
Each item is a change on the Rust side with its own ADR or spec line; Studio shows the feature only when it exists.

1. **Approvals through the gateway.** `approve` takes one human `ptok` per request key; a browser or app user has no key. The gateway should add them for a logged-in user, as it adds flow deploy proofs (`add_flow_proofs` in `crates/wyrm-gateway/src/ws.rs`), for the ticked steps only.
2. **Conversation.** `ask {task}` starts a task; a chat needs follow-ups in the same task (`reply {text}`) with the earlier turns in the model's context.
3. **Clarifying choices.** A model tool that asks the user (`question`, `options[]` taken from the tree), a state `awaiting_answer`, and `answer {choice}`.
4. **Plan steps beyond set/invoke.** `wait`, `expect` and `deploy` exist in `wyrm-agent` plans (ADR 0033) but not in the agent link (`flow_apply` is "not supported yet").
5. **Progress per step.** The public `~val` of a task is `{state}`; the run card needs the current step (and its answer) without reading `~state` again.
6. **Approving part of a plan.** Check that the executor runs only the steps with a token and records the rest as skipped.
7. **A dry run of a package.** `sys/links` ▸ `check_package {zip | url | git | repo}` → the checks of docs/links.md §4 and the manifest, installing nothing, so Studio does not keep a second copy of the rules.
8. ~~**Own blocks (sub-flows)** in the flow engine: a block whose fields are the inputs and outputs of an inner graph.~~ **Done** (ADR 0040 §3, spec 06 0.2.24; Studio: §7.6 "Custom blocks", `flow-editor.md` §20). Still open on the engine side, each small: a row of its own for an instance in `watch`; a `trigger` (Run) for the readers `load_value` and `list_children`; command targets from a port (ADR 0040 §1a).
9. **Repeat**: one instance of a block per row of a table input, keyed by a column.
10. **A web transport** for `wyrm_client` (`package:web` WebSocket and fetch) if Studio should run in a browser.
11. **Documents through the gateway.** A task's full record is the `~state` document of `tasks/<id>` (the public `~val` is `{state}` only); the gateway has no op that reads `~state`/`~def` documents (`ws.rs`: `meta`, `children`, `list`, `subscribe`, `history`, `set`, `invoke`), so the Assistant cannot show a plan until it has one (`doc {key, suffix}`, rights as `list` on the node, as the agent's `restricted` folder asks).
12. **Which secrets a link has.** `sys/links/<id>` has `set_secret`/`delete_secret` but no read of the secret names, so Studio cannot say whether the agent's API key is set; it shows the `api_key_ref` name. A `secrets` value (names only, level `config`) would let it say "not set" and offer Set secret.
13. **Gateway info before login.** The log-in page shows a gateway's site and wyrmd version beside its address; today the gateway tells them only after login. A public `GET /api/info {site, version, tls}` would close that.
14. **The list of profiles.** `sys/profiles` has `put` and `remove` but no children, and `wy/<site>/pub` answers `not_found` to a list (`serve_profiles` answers `pub/<name>/~meta` only), so Studio cannot list the profiles it could remove: System › Maintenance shows the broker's answer instead of rows. A `view=list` answer on `pub` (names, user profiles apart from the built-ins) would fill the list.
15. **Why a link failed.** `sys/links/<id>` serves `state` and `log_level` only; the attention card of a failed link has no `error` text to show (the board shows one) and points at the link's log.
16. **The broker's liveliness through the gateway.** The token `wy/<site>/sys/broker` is not visible to a gateway user; System reads the gateway connection instead (pill `Unreachable`, the Liveliness fact).
17. **The host's paths.** `sys` serves neither `data_dir` nor the config path, so the backup commands always carry `/var/lib/wyrm` and `/etc/wyrm/wyrmd.json5`.
18. **The audit tail by operation.** `sys/audit ▸ tail {n}` has no filter, so `Open the audit record ›` opens Access › Audit unfiltered, not at `standby_forked`.
