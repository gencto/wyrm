# 06 — `dataflows/<id>/~def`

CBOR map (на дроті) / JSON (у конфігах і UI) — одна схема. Рядкові ключі (користувацький вміст).

```
{
  "id": tstr,                 // = сегмент ключа
  "version": uint,            // монотонно; engine ігнорує ≤ поточної
  "enabled": bool,            // default true
  "description": tstr?,
  "nodes": { <node_id>: { "type": tstr, ...config, "placement": "local"|"process"|"wasm"? } },
  "edges": [ [ "<node>.<port>", "<node>.<port>" ] ],
  "policy": { "overflow": "drop_oldest"|"drop_newest"|"block", "queue": uint, "state_flush_s": uint, "restart": {"backoff_max_s": uint} },
  "permissions": { "token": tstr, "maxperm": uint },
  "layout": { <node_id>: [ x, y ] },  // 0.2.5: де редактор малює ноду; компілятор не зважає
  "blocks": { <name>: { "description": tstr?, "inputs": [ {"name": tstr, "to": tstr | [tstr], "default": any?, "description": tstr?} ],
                        "outputs": [ {"name": tstr, "from": tstr, "description": tstr?} ],
                        "nodes": {…}, "edges": […], "layout": {…}? } }   // 0.2.24: власні блоки
}
```
Порти: `<node>.out`, `<node>.in`, іменовані `<node>.in.<name>` / `<node>.out.<name>` (у `expression` — `in.<input>`; у `alarm` — `out`, `event`).

Поля як виходи (0.2.15, ADR 0038): кожне поле ноди є також виходом, з якого може починатися ребро.
- Параметр `p` дає вихід `p` з ефективним значенням: з конфігу або default, а де є порт `in.<p>` — останній семпл на ньому. Вихід надсилає значення один раз на старті і далі на кожну зміну.
- Вхід `x`, що не є портом параметра (`in`, `reset`, `in.0`, …), дає вихід `x`. Він повторює кожен семпл на `x` до того, як нода його обробить.
- Назва виходу така сама, як у поля: `scale1.input_min`, `if1.in.0` (ребро ділиться на першій крапці: нода `if1`, порт `in.0`).
- Конфлікт назв: оголошений вихід ноди лишає свою назву; ехо входу йде перед ехо параметра. Тому параметр `reset` у `latch` (є вхід `reset`) не має виходу (`echo: false` у каталозі).
- Тип виходу: ехо входу — тип входу; ехо параметра — `number`, `bool`, `map` за типом параметра, інші (`string`, `dynamic`, `array`) — `any`. Крок 4 валідації перевіряє ці типи, як і решту.
- Ехо-вихід, з якого не йде жодне ребро, не будується: runtime не копіює для нього семпл.

Порти параметрів старших типів нод (0.2.17, ADR 0038 §5a): `scale` — `in.k`, `in.b`; `alarm` — `in.high`, `in.low`, `in.hysteresis`, `in.delay_s`, `in.return_delay_s`; `delay` — `in.ms`; `window` — `in.size_s`; `deadband` — `in.abs`, `in.pct`; `timer` — `in.period_ms`. Усі мають тип `number`. Правило як у логічних блоків: значення з конфігу або default на старті, далі перемагає останній добрий семпл. Семпл, що не є скінченним числом або виходить за межі параметра (`period_ms` ≥ 10, `size_s` > 0, `ms` ≥ 0, `delay_s` і `return_delay_s` ≥ 0), ігнорується. Правила конфігу не змінюються (`high` або `low`, `abs` або `pct` тощо обов'язкові). Новий `period_ms`, `ms`, `size_s` або затримка `alarm` діє одразу: годинник ноди починається заново через один період після зміни.

Блоки як у DGLux (0.2.21, ADR 0038 §8; повний опис — `docs/flow-blocks.md`): `if.op` має ще `!=` (перший вхід не дорівнює жодному з інших), `contains`, `starts_with`, `ends_with` (перший вхід як текст з будь-яким з інших як текстом). `round` має параметр `min_precision` (порт `in.min_precision`) і вихід `text`: число з `precision` знаками, кінцеві нулі обрізано до `min_precision` знаків (default — `precision`). Новий блок `case`: вхід `in`, параметри `op` (`=`, `!=`, `>`, `<`, `>=`, `<=`, `contains`, `starts_with`, `ends_with`) і `else` (default null), змінні входи `inputs` парами (case, then); вихід `out` — then першої пари, чий case збігається з `in` за `op`, інакше `else`. Порожній текст case нічого не збігає.

Порти решти параметрів блоків (0.2.20): `concat` — `in.strict`; `if` — `in.op` (лише відомий оператор, інший текст ігнорується); `hub` — `in.ignore_null`; `trace` — `in.tracing`, `in.msg`. Тепер кожен параметр логічного блоку має порт, крім `value` змінних (його замінює вхід `in`) і `inputs`.

Константи операндів (0.2.19, ADR 0038 §7): логічний блок має ключ конфігу `values: {<port>: <value>}`, наприклад `{type: "concat", values: {"in.0": "AHU-", "in.1": 2}}`. Ключ — операнд блоку: `in` (якщо блок його має) або `in.<name>` з його `inputs`. Не можна: порт параметра, `reset` у `stopwatch`, змінні (`number`, `string`, `bool` мають `value`). Інакше — помилка компіляції `values.<port>: not an operand input`. Константа — значення входу, доки семпл на цьому вході її не замінить (прив'язка перемагає). Константа нічого не обчислює: блок обчислює на першому справжньому семплі, як і раніше. Тому deploy, гаряча заміна і перезапуск ніколи не виконують `set` або `invoke` через константу. `watch`, `ports` і `preview` показують константу як значення входу від старту. Каталог: `values: true` у типів, чиї операнди беруть константу.

Ключ з порту в межах scope (0.2.22, ADR 0040 §1): `subscribe` і `liveliness` мають вхід `in.key`, вихід `error` і параметр `key_scope`.
- `key` у конфігу — стартовий ключ. Його може не бути, якщо є `key_scope`.
- `key_scope` — key expression (відносний від `wy/<site>/` або повний), наприклад `downstream/modbus/line1/**`. Він обов'язковий, коли в `in.key` входить ребро: інакше помилка компіляції `nodes.<id>.key_scope: required when in.key is wired`. Scope за замовчуванням немає.
- Scope лежить у `downstream`, `dataflows` або `storage` свого сайту (крок 9). Секція є літеральним префіксом scope.
- Deploy: `auth` деплоєра дає `read` на весь scope. Гранти читаються по порядку: грант нижче `read`, що перетинає scope, відмовляє; грант `read`, що покриває весь scope, дозволяє; грант `read` на частину лишає решту наступним грантам. `watch`, `ports` і `preview` перевіряють те саме для того, хто викликає.
- Runtime приймає значення з порту, лише коли воно: текст; не порожнє; не довше 512 байтів; один конкретний ключ вузла (кожен сегмент `[A-Za-z0-9_.-]+`: без `*`, `**`, `$*`, без `~meta`, без порожніх сегментів); у секціях свого сайту; у межах scope.
- Новий ключ: спершу закінчується старе читання, `out` надсилає `null` з якістю `uncertain` і лишається таким до першого семпла нового ключа. Ефективний `key` (ехо-вихід `key`, `params.key` у `watch`) — ключ, як його написано.
- Відмова: нода нічого не читає, `out` — `null`/`uncertain`, ефективний `key` — `null`, вихід `error` несе причину текстом. `error` повертається до `null` з наступним прийнятим ключем.
- `null` на порту: нода нічого не читає, помилки немає.
- Між двома змінами ключа минає щонайменше 100 мс. Значення, що прийшло раніше, чекає; перемагає останнє.
- Цілі команд (`set.path`, `invoke.path`, `invoke.action`) і `publish.node` портів не мають (ADR 0040 §1a).
- Каталог: `params[].scope` — назва параметра, що тримає scope цього поля (`key` → `"key_scope"`).

Блок дії та поведінка команд (0.2.23, ADR 0040 §2): `invoke` і `set` мають поля поведінки, вхід `trigger` і виходи-події.
- Аргументи `invoke`: кожен ключ мапи `args` — аргумент. Значення ключа — константа аргументу. Порт `arg.<name>` замінює її останнім семплом. Не більше 64 аргументів; назва має 1–128 байтів і не починається з `__`. Константа `"$in"` означає останнє значення на `in`.
- `interval_ms` (порт `in.interval_ms`, default 0): 0 — вимкнено; інакше 100 … 86 400 000. Нода запускається кожен період, уперше — через повний період після старту. Період пропускається, доки попередній запуск не отримав відповіді.
- `auto_run` (порт `in.auto_run`): у `invoke` (default false) семпл на `arg.<name>`, що змінює аргумент, запускає дію. У `set` (default true) значення на `in` записується, як раніше; `false` — `in` лише тримає значення.
- `enabled` (порт `in.enabled`, default true): `false` — ноду нічого не запускає.
- `run_on_start` (bool, default false, без порту): `true` — нода запускається рівно один раз на кожен старт флоу (deploy, гаряча заміна, reload, перезапуск), через 250 мс після старту ноди. Це єдиний дозволений виняток з правила старту, і його обирають для кожного блоку окремо. Вимкнена нода стартового запуску не робить. `set` пише значення, яке `in` отримав до цього моменту, і не пише його вдруге після `auto_run`. У preview стартовий запуск — це рядок `sinks`, а не запис.
- Один блок, а не окремий тип на кожну поведінку: поведінку задають поля `trigger`, `auto_run`, `interval_ms`, `enabled`, `run_on_start`. Старий `on` у `invoke` діє лише для `in`, як раніше (`change` відповідає `trigger` зі значенням; `rising`/`falling` — блоку фронту перед `trigger`).
- Вхід `trigger`: подія `{event, id}` запускає ноду; інше значення запускає її, коли воно відрізняється від попереднього семпла на `trigger`. `null` і семпл якості `bad` (без `allow_bad`) нічого не запускають.
- `in` працює, як раніше: `invoke` запускається на кожен семпл, що проходить `on`; `set` бере значення для запису.
- Виходи обох типів: `sent` (подія: запит пішов), `ok` (подія: ціль відповіла без помилки), `error` (подія `{event, id, code, message}`: `code` — код статусу spec 04), `running` (bool), `last_run` (час останнього `sent`, мкс). `invoke` має ще `result` (останній результат) і `out` (результат з якістю `good` або текст помилки з якістю `bad`, як раніше).
- Правило старту: семпл «народжений на старті» ніколи не запускає команду через `trigger` або `auto_run`. Такими є: стартове значення змінної та `const`, стартове значення ехо параметра, тік годинника на старті, перший семпл читання (`subscribe`, `liveliness`), а також усе, що нода надсилає, обробляючи такий семпл. Тому deploy, гаряча заміна, reload і перезапуск не виконують команду через `trigger`, `auto_run` чи `interval_ms`. `in` цього правила не має (див. УВАГА нижче).
- `dataflows/<id>/~act/trigger {node}` — рівень `write`; один запуск ноди `invoke` або `set` задеплоєного флоу, що працює. `auth` того, хто викликає, дає на ціль ноди (`…/~act/<a>` або `…/~set`) рівень `max(maxperm, write)` — той самий, що deploy вимагає від proof деплоєра; інакше `permission_denied`. Інша нода — `invalid_parameter`; флоу не працює — `not_supported`.
- У preview `set` та `invoke` не мають клієнта: вони повідомляють у `sinks`, що надіслали б, дають `sent` і `last_run`, і ніколи не дають `ok`, `error`, `result`, `out`, `running`.
- Каталог: `dyn_inputs.keys: true` — параметр є мапою, порти названі її ключами (`invoke.args` → `arg.<name>`); `trigger: true` у типів, які запускає `~act/trigger`.

УВАГА: ехо параметра надсилає значення на старті. Ребро з нього до `invoke` або `set` виконує команду при deploy.

`layout` належить редактору (ADR 0019): ключ — `node_id`, значення — два скінченні числа. Він не входить до конфігу ноди, тож переміщення ноди не скидає її стан при гарячій заміні.

Каталог типів нод для редактора: `dataflows/~act/node_types` (рівень `read`) повертає масив `{type, category, description, inputs, outputs, dyn_inputs?, dyn_outputs?, port_types, echo_inputs?, values? (0.2.19), params: [{name, type, required, description, choices?, default?, editor?, port?, scope? (0.2.22), echo}]}`; `dyn_inputs`/`dyn_outputs` = `{param, prefix, default}` — порти, які дає параметр (`expression`: `in.<name>` з `inputs`; `wasm`: `inputs`/`outputs`).

Поля 0.2.15 (ADR 0038, лише додані):
- `params[].default` — типізоване значення для кожного параметра, що його має: число лишається числом, `choices` — рядком, список імен — масивом (`inputs` блоків: `["0", "1"]`). Без default поля немає.
- `params[].port` — `"in.<p>"`, коли в параметра є вхідний порт; інакше поля немає.
- `params[].echo` — `true`, коли параметр має вихід своєї назви; `false` при конфлікті назв (див. «Поля як виходи»).
- `port_types` — `{<port>: <type>}` (`number`, `bool`, `map`, `any`) для фіксованих входів і виходів, для динамічних портів з їхніми `default` і для ехо-виходів. Динамічні порти з іншими назвами мають тип `any`.
- `echo_inputs: true` — входи типу, що не є портами параметрів, повторюються як виходи. У типів без входів поля немає.

## Власні блоки (0.2.24, ADR 0040 §3)
Визначення може мати `blocks`. Нода типу `block:<name>` — екземпляр блоку `<name>`.
- `inputs` і `outputs` блоку — списки (редактор малює поля в цьому порядку). Назва — `[A-Za-z0-9_]+`, унікальна серед входів і виходів разом. Не більше 64 входів і 64 виходів. `to` — один внутрішній вхід `"<inner>.<port>"` або список з 1–16 таких; `from` — внутрішній вихід.
- Параметр блоку — це вхід з `default`. Окремого списку параметрів немає.
- Екземпляр має лише ключ `values: {<input>: <value>}`. Його порти — входи й виходи блоку: `["x.out", "m1.a"]`, `["m1.out", "y.in"]`. Вхід є також виходом своєї назви (ехо першого внутрішнього входу з `to`).
- Компілятор замінює екземпляр внутрішніми нодами з id `<instance>/<inner>` (у вкладеному блоці — `<instance>/<inner instance>/<inner>`). Авторський id не містить `/`.
- Константа входу (`values` екземпляра, інакше `default`) стає константою кожного внутрішнього входу з `to`: порт параметра → конфіг параметра; операнд логічного блоку → його `values`; `arg.<name>` у `invoke` → `args`; `in` змінної → `value`; вхід внутрішнього екземпляра → його `values`. Вхід, що не тримає константи (`filter.in`, `set.in`), дає помилку `nodes.<id>.values.<input>: <inner>.<port> takes no constant`.
- Блок може містити екземпляри інших блоків того самого визначення. Глибина — не більше 4; блок, що містить себе, відхиляється. Ліміт 1000 нод рахує розгорнуті ноди. Не більше 64 блоків у визначенні.
- `publish` усередині блоку має одну назву в кожному екземплярі, тому такий блок можна вжити один раз (крок 7a).
- `watch`, `ports` і `preview` показують внутрішні ноди під їхніми id: `nodes: {"m1/sum": {…}}`. Аргумент `nodes` приймає id екземпляра і тоді означає всі його внутрішні ноди. Окремого рядка екземпляр не має. `~act/trigger` приймає внутрішній id.
- `~def` та історія зберігають визначення, як його надіслано, разом з `blocks`.

Бібліотека блоків сайту (дії на `dataflows`):
- `put_block {name, def}` — рівень `config`; `def` — один блок. Engine перевіряє його, як deploy: сам у пробному флоу, з блоками бібліотеки, які він вживає. Відповідь `{name, version}`; кожен `put` — наступна версія. Не більше 256 блоків, 256 КіБ на блок.
- `get_block {name}` — рівень `read`; відповідь `{name, version, def, requires: {<name>: def}}` з усіма блоками бібліотеки, які він вживає.
- `list_blocks` — рівень `read`; `[{name, version, description?, inputs: [назви], outputs: [назви]}]`.
- `remove_block {name}` — рівень `config`; `not_found`, якщо блоку немає.
- Флоу копіює блок, а не посилається на нього: редактор бере блок через `get_block` і записує його (та `requires`) у `blocks` визначення. Engine під час компіляції бібліотеку не читає.

## Валідація (порядок, перша помилка зупиняє)
1. схема; 2. унікальність `node_id`, `[A-Za-z0-9_]+`; 3. тип ноди є в реєстрі, конфіг за схемою типу; 4. ребра → існуючі порти, сумісні типи; 5. ациклічність (цикл дозволений лише через `delay`); 6. rhai компілюється; 7. `permissions.maxperm` ≥ мін. рівня всіх `invoke/set`-нод і ≤ `write` (флоу не робить config-операцій); 8. ліміти пам'яті (`window.max_samples` сума; з 0.2.16 — не більше 1000 нод у флоу: кожна нода — це задача і черга під час роботи, у задеплоєному флоу і в preview); 9. (0.2.13) `key` кожної ноди `subscribe` і `liveliness` лежить під `wy/<site>/downstream`, `wy/<site>/dataflows` або `wy/<site>/storage` свого сайту (відносний ключ читається від `wy/<site>/`): не `sys`, `pub`, `upstream`, не інший сайт. Engine читає через сесію broker'а, якої ACL не бачить, тому правило перевіряє deploy, validate і старт збереженого флоу. З 0.2.22 те саме правило діє для `key_scope`, а крок 4 має додаток 4a: ребро в `in.key` потребує `key_scope` у конфігу ноди.

Помилка → `dataflows/<id>/~val = {state: 2 (error), error: "<path>: <msg>"}`; стара версія працює.

## `~val` флоу
`{0: {"state": 0 running | 1 stopped | 2 error, "error": tstr?, "version": uint, "since": uint, "deployed_by": tstr?}, 1: q, 2: t}`

`deployed_by` — суб'єкт, що задеплоїв поточну версію (`origin` запиту або `sub` токена). Флоу працює далі, навіть якщо деплоєр втратив права (ADR 0008); поле дає оператору знайти такі флоу.

## Живі значення (0.2.15, ADR 0038)
`dataflows/<id>/~act/watch` — рівень `read`, `stream: true`, `timeout_ms: 30000`. Аргументи: `nodes` (масив id нод; немає або порожній — усі; невідомий id — `invalid_parameter`), `max_hz` (число > 0 і ≤ 20, default 4).

Права: `auth` у `ptok` того, хто викликає (spec 04), має покривати читання кожного джерела флоу (`subscribe`, `liveliness`), як при deploy, і кожної цілі команд (вузол кожної ноди `invoke` і `set`, без `~act/<a>` чи `~set`). Вихід `invoke` несе відповідь цілі, а вхід `set` — те, що нода туди пише. Інакше — `permission_denied`. Помилка engine називає перший ключ, але SDK надсилає цей статус без тексту. Флоу без джерел і без цілей не потребує `auth`.

Рядки (CBOR map, текстові ключі; `[v, q]` — значення і код якості, як у `~val`):
1. перший: `{t, snapshot: true, nodes: {<node>: {in: {<port>: [v, q]}, out: {<port>: [v, q]}, params: {<p>: v}}}}` — кожна нода (або з `nodes`), усі три мапи завжди є; `params` — ефективне значення кожного параметра, що його має;
2. далі: `{t, snapshot: false, nodes: {…}}` — лише ноди і порти, що змінилися після попереднього рядка; порожні `in`/`out`/`params` пропущено. Не більше `max_hz` рядків на секунду; у межах періоду перемагає останнє значення;
3. heartbeat `{t, nodes: {}}` (без `snapshot`), коли 10 с не було рядка;
4. потік закінчується через 30 хв (ttl), при redeploy (останній рядок `{t, redeployed: <version>}`), при remove і при зупинці engine (без рядка). Редактор відкриває його знову.

Engine зберігає останній семпл кожного входу і виходу задеплоєного флоу від старту, навіть без відкритого `watch` (0.2.18). Один слот на порт; новий семпл перезаписує його. Тому змінна, що надіслала значення один раз на старті, є в кожному пізнішому snapshot і в `ports`. Порт без жодного семпла від старту відсутній у `in`/`out`.

Ліміти: ≤ 8 `watch` на флоу, ≤ 64 на сайт. Engine не бачить, що той, хто викликає, пішов: на ліміті новий `watch` того самого суб'єкта (`origin` або `sub`) закриває його найстаріший `watch` (на флоу, а на ліміті сайту — будь-який його); `watch` іншого суб'єкта отримує `busy`.

`dataflows/<id>/~act/ports` — рівень `read`, аргумент `nodes`, ті самі права; повертає рядок 1 (для інструментів без потоку: `wyrm-agent`, MCP) з усіма значеннями портів від старту флоу.

Значення ніколи не пишуться в лог вище `trace`.

## Preview чернетки (0.2.16, ADR 0038 §5)
`dataflows/~act/preview` (на корені `dataflows`) — рівень `read`, `stream: true`, `timeout_ms: 30000`. Аргументи: `def` (визначення в тій самій формі, що й для `deploy`), `nodes` (масив id нод, як у `watch`), `max_hz` (число > 0 і ≤ 20, default 4).

- `def` компілюється, як при deploy і validate (усі кроки валідації). Помилка — `invalid_parameter` з текстом компілятора. `maxperm` і `proofs` не потрібні: preview нічого не пише.
- Права — як у `watch`: `auth` того, хто викликає, покриває читання кожного джерела і кожної цілі команд. Інакше — `permission_denied`.
- Чернетка працює в пісочниці: справжній runtime без збереження (ні `~def`, ні стану нод), без вузла в дереві, з id поза задеплоєними флоу. Чернетка з id задеплоєного флоу не торкається ні цього флоу, ні його `watch`. Читання йде через клієнт без токенів.
- Ноди `set`, `invoke` і `publish` у preview — це ноди-записувачі без клієнта: вони не можуть писати за побудовою. Вони застосовують те саме правило, що й задеплоєна нода (`allow_bad`, `on`, `deadband`, `$in` в `args`), і лише повідомляють результат. `invoke` у preview нічого не надсилає на `out`.
- Рядки — точно як у `watch` (snapshot, зміни ≤ `max_hz`, heartbeat `{t, nodes: {}}` через 10 с). Будь-який рядок може мати ключ `sinks: [{node, op, key, value}]`: `op` — `set`, `invoke` або `publish`; `key` — повний ключ, куди нода писала б (`wy/<site>/<path>/~set`, `wy/<site>/<path>/~act/<action>`, `wy/<site>/dataflows/<def.id>/nodes/<node>`); `value` — значення, а для `invoke` — мапа аргументів після `$in`. Snapshot має останнє від кожної такої ноди; рядок змін — ті, що спрацювали після попереднього рядка, останнє на ноду. Рядок лише з `sinks` — це рядок змін (`snapshot: false`, `nodes: {}`). `nodes` фільтрує і `sinks`.
- Запис іде від старту: перший рядок чекає (≤ 500 мс), доки всі ноди запустяться і стихнуть. Тому snapshot уже має стартові значення змінних і те, що вони дали далі.
- Preview закінчується через 10 хв (ttl), коли новий preview того самого суб'єкта займає його місце, при panic ноди (потік закінчується зі статусом `internal_error`, без перезапуску) і при зупинці engine. Редактор відкриває його знову з останньою чернеткою. Таймери, `stopwatch`, `delay`, `window` працюють як завжди.
- Ліміти: ≤ 2 preview на суб'єкта (`origin` або `sub`; третій закриває найстаріший), ≤ 16 на сайт (`busy` понад це). Engine не бачить, що той, хто викликає, пішов: preview живе до ttl або до заміни.
